# Qiehao

[简体中文](README.md) | [English](README.en-US.md)

Qiehao 是面向 Windows Codex Desktop 的本地多账号管理工具。切换账号后，原有本地项目文件仍可继续使用；管理三个及以上账号时，减少反复登录和切换操作的优势更明显。账号切换由用户手动触发，并须等待 Codex 完全退出。

支持 Plus、Team 等账号的本地档案管理与切换。如果你使用的官方账号切换方式只提供两个账号位置，Qiehao 更适合保存和管理三个及以上账号，并在同一电脑、同一路径继续使用原有项目文件；这里不把“两个账号”视为所有官方客户端版本的永久限制。

**本地项目连续使用仅指磁盘上的项目文件仍在原路径可用。** Qiehao 不提供官方聊天记录、项目元数据或 Memory（记忆）的账号间同步，也不合并不同账号的云端数据。

> [!IMPORTANT]
> Qiehao 是非官方社区工具，不是 OpenAI 官方产品。它只管理 Codex Desktop 的本地认证状态，不修改 ChatGPT Web、浏览器或 PWA（渐进式网页应用）的登录状态。

> [!NOTE]
> **最新正式版本：Qiehao v1.1.1（2026-11-02）。** 本版包含 OAuth 异常后的只读身份核对、明确确认保存新档案、受控 Team 恢复及额度缓存身份绑定。请从 GitHub Releases 下载正式 Windows ZIP 并核对 SHA-256；`Code → Download ZIP` 是源码快照，不是正式程序包。Codex Desktop 偶发未登录及官方 OAuth 完成通知被拒绝仍属于已知限制。

## 使用提醒

1. 切换账号前正常退出 Codex Desktop，确认后台客户端进程也已退出。
2. Codex 运行期间，账号删除受到保护；不要通过强制结束进程绕过提示。
3. OAuth（开放授权）成功不等于本地档案保存成功，请以 Qiehao 最终结果及账号列表为准。
4. “检查当前登录身份（只读）”不会自动保存账号；新增档案需要身份验证和另行确认。
5. 额度查询失败不能当作刷新成功，保留的历史数字也不是本次查询结果。
6. 历史缓存“归属未验证”表示无法确认其属于哪个已保存档案，不等于从未获取过额度。
7. 旧缓存需对当前账号成功刷新并建立新的身份绑定后，才能作为可信额度快照。
8. Codex 启动后暂时显示未登录时，先等待客户端初始化；持续异常再完全退出并重新打开，必要时检查脱敏日志。不要连续重复切号或手工复制 `auth.json`。如出现“请勿启动 Codex／需要人工检查”，优先遵守该停止提示。

## 先说最重要的：Qiehao 不反代

Qiehao **不是反代工具，也不准备往反代方向做。**

不反代，不轮询，不做额度池。

它不代理 Codex 或 API 流量，不帮你转发请求，不做账号池，不做自动轮换，不根据额度自动换号，也不会碰到 HTTP 429 就自己切另一个账号。

如果你找的是反代、自动养号、后台账号池、无人值守自动切号这一类东西，那这个项目不用继续往下看了。

我做它就是想把“我自己正常登录、自己正常使用的几个账号，切起来别那么折腾”这件事情做好。

## 我为什么会做 Qiehao

我做 Qiehao 的原因其实特别简单：

**我真的受够了切账号时那个 OAuth 登录页面一直转圈圈。**

本来只是想换一个自己正常使用的账号，结果经常要退出、重新登录、等 OAuth 页面、再等 Codex 认账号。网络或者登录状态稍微不顺一点，就在那里一直转。有时候转半天都登不上，如果几个自己正常使用的账号来回切，真的挺头疼。

所以我最开始想做的，并不是什么“绕过登录”的东西。恰恰相反，我做的是：

**能不能第一次老老实实走官方登录，以后在本机把已经正常登录过的账号安全保存下来，需要的时候再规规矩矩切回来？**

所以 Qiehao 的基本原则一直没变：

- 新账号第一次仍然走 Codex 官方 OAuth；
- 不模拟登录；
- 不抓浏览器 Cookie；
- 不接管 ChatGPT Web/PWA；
- 不反代；
- 不做自动账号池；
- 不在后台轮询多个账号；
- 每次切号都由人自己点；
- Codex 没真正退出，就不动认证文件。

说白了：

**它不是帮我养一池账号，而是让我切自己正常用的账号时，减少输密码与等待。**

## 我对使用方式的想法

我个人的想法也很简单：

**能规规矩矩用，就规规矩矩用，求的是长期稳定。**

所以这个工具没有做多账号后台轮询，没有做额度触发自动切号，没有做 429 自动换号，也没有做无人值守账号池。

能走官方登录就走官方登录，能走 Codex 自己提供的接口就用它自己的接口。能少做一次没必要的请求，就少做一次。能不自动化的地方，我宁愿让人自己点一下。

我当然也希望这种比较老实的用法，能够少碰一点莫名其妙的风控，少一点大家平时说的“降智”，也尽量降低账号被限制甚至封号的概率。

但这句话只是我自己的使用思路和期望，不是平台给出的承诺，Qiehao 也不可能保证：

- 一定不会风控；
- 一定不会降智；
- 一定不会限制；
- 一定不会封号。

平台规则、风控和模型行为都不是 Qiehao 能控制的。

Qiehao 能做的，只是尽量不要自己主动增加那些没必要的高频轮询、自动切号、异常请求和过度自动化行为。

**不想着钻空子，规规矩矩用，这就是我做这个工具时给自己定的方向。**

## 项目定位

- 仅面向 Codex Desktop，不支持自动账号轮换。
- 不读取浏览器 Cookie（浏览器凭据）、LocalStorage（本地存储）或 IndexedDB（浏览器数据库）。
- 不修改或退出 ChatGPT Web/PWA 会话。
- 不根据 Quota（额度）、HTTP 429 或其他错误自动切号。
- 不做 round-robin（轮询轮换）或后台自动切换。
- 每次账号切换都必须由用户明确触发。

## 工作方式

v1.1.1 添加账号时，Qiehao 委托官方 Codex app-server（应用服务进程）发起 ChatGPT 浏览器 OAuth（开放授权）；用户在官方登录页完成登录。Qiehao 验证身份后，将原始认证状态保存为由 Windows DPAPI CurrentUser（数据保护 API，当前用户作用域）保护的加密快照。不支持该协议时，界面明确提示使用原来的手动导入流程。

后续切换时，Qiehao 要求 Codex Desktop 完全退出，然后安全回存当前账号、验证目标账号、原子替换 Codex 本地认证文件、读回校验，最后更新本地 Active Profile（当前活动档案）状态，并分别报告本地切换与官方验证结果。Qiehao 不自动填写登录信息、不实现自己的 OAuth 登录接口、不强制终止 Codex，也不接触浏览器登录态。

## 安全设计

- **Manual-only switching（仅手动切换）**：切换只由用户点击发起。
- **DPAPI CurrentUser（当前用户加密）**：认证快照和身份标记只能由同一 Windows 用户解密。
- **Atomic replace（原子替换）**：关键文件使用同卷临时文件和原子替换，避免半写入状态。
- **Reread verification（读回验证）**：替换后重新读取并逐字节核对目标内容。
- **Rollback（回滚）**：替换后验证或状态提交失败时，尝试恢复原活动账号。
- **Named mutex（命名互斥锁）**：写操作串行化，避免多个实例并发修改。
- **Process gate（进程门禁）**：仅在 Codex 已确认完全退出时执行认证写操作。
- **Unknown fail closed（未知状态安全拒绝）**：无法可靠判断进程或认证状态时停止，不冒险继续。
- **No forced kill（不强杀）**：要求用户从 Codex 官方菜单或系统托盘正常退出。
- **Browser/PWA untouched（浏览器/PWA 不受影响）**：不读取或修改浏览器会话数据。

DPAPI CurrentUser 主要保护认证快照的静态存储，避免明文落盘。它不能防御已经能够以同一个 Windows 用户身份运行的恶意程序，也不意味着认证数据绝对安全、永远无法解密或永远不会被窃取。

Qiehao 不保存账号密码、不抓浏览器 Cookie、不逆向 OAuth，也不使用 `chatgptAuthTokens` internal-only（仅供内部使用）模式。正常登录委托官方 Codex Managed ChatGPT OAuth（托管登录）；不上传 `profiles/`、`state/` 或认证文件，不把 Token（令牌）、邮箱、完整账号 ID 或 JWT（身份令牌）写入诊断日志。

## Quota Snapshot（额度快照）

额度快照通过官方 Codex app-server 的 `account/rateLimits/read` 接口读取当前 Active Profile 的额度信息。这是 Best Effort（尽力而为）的辅助功能，依赖官方接口和网络状态；可能超时、暂时失败，或收到缺少部分额度窗口的响应：

- 只主动查询当前 Active Profile；
- inactive profile（非活动档案）只显示最后一次成功缓存；
- 不持续轮询，不构成实时额度监控；
- 查询失败时保留旧快照，不清零、不伪造更新时间；
- 快照只代表最后一次成功查询结果，不保证实时性；
- 额度失败不会自动触发账号切换。

### 关于额度查询速度

先说一下这个功能最容易让人觉得“不爽”的地方：

**额度查询有时候确实会慢。**

Qiehao 没有自己去抓网页，也没有自己搞一套私有额度接口。它用的是 Codex 自己的 app-server 接口，去读取当前活动账号的额度快照。

所以额度查询属于 best effort（尽力而为）：

**能查到就查，查不到就保留上一次结果，不保证每次一点刷新就马上秒回。**

有些时候 Codex app-server 启动会慢一点，有些时候返回额度会慢一点，也可能直接超时。这部分体验确实没有“点一下立刻出结果”那么爽，我知道。

但是我不想为了把界面做得看起来更快，就改成：

- 抓网页登录页面；
- 偷读浏览器 Cookie；
- 后台不停轮询；
- 同时去探测多个账号；
- 接第三方私有额度接口；
- 因为额度没回来就自动换号。

所以这里我宁愿接受它偶尔慢一点。

查询失败的时候，Qiehao 会尽量保留上一次成功的额度快照，让你之后自己再点一次刷新。

这也是为什么这个功能叫 **Quota Snapshot（额度快照）**，而不是 **实时额度监控**。

还有一个很重要的区别：

**额度刷新慢或者失败，不代表账号切换失败。**

账号切换和额度查询是两个不同的流程。我的取舍很简单：

**切号优先保证安全和正确；额度查询允许慢一点，也允许偶尔失败。**

额度查询属于辅助功能，不影响账号添加、切换和删除。

如果额度获取失败，可点击“刷新额度”重新获取。

普通用户请从 GitHub Releases 下载最新的 Qiehao Release ZIP（发布压缩包）：

1. 下载最新 Release ZIP。
2. 将 ZIP 完整解压到本地普通用户具有读写权限的目录。
3. 不要直接在 ZIP 压缩包内运行程序。
4. 普通用户只应双击从 GitHub Releases 下载并完整解压的正式 Windows ZIP 根目录中的：

~~~text
Qiehao.exe
~~~

推荐双击 `Qiehao.exe`。它是 Windows GUI Launcher（图形界面启动器），正常情况下不会显示命令行黑框。启动器只调用系统 Windows PowerShell 5.1，脚本和模块仍独立保留。

**普通用户不要从 Git 源码仓库目录启动 `Qiehao.exe`，也不要把 GitHub 的 `Code → Download ZIP` 源码快照当作运行目录。** 源码仓库仅用于开发和版本管理。Qiehao 可能在程序所在目录旁创建 `profiles/`、`state/`、`logs/`、`backup/` 等本机运行数据；`.gitignore` 只阻止 Git 跟踪这些文件，不会阻止它们写入磁盘。

如果 EXE 无法启动，使用 `Start-Qiehao.cmd` 作为兼容／排障入口。两个入口最终启动同一套 Qiehao 程序逻辑。

`Qiehao.exe` 当前未进行商业代码签名。请核对 GitHub Release（正式发布）来源，并使用随包 SHA256 校验文件验证完整性；哈希校验不等同于数字签名。

Qiehao 不需要管理员权限，也不需要安装 Node.js、Python、Visual Studio 或第三方 PowerShell 模块。

普通用户无需执行 PowerShell 命令，该命令仅用于高级用户排障：


这里的 ExecutionPolicy Bypass（绕过执行策略）只应用于本次启动的 PowerShell 进程，不会永久修改系统 PowerShell 执行策略，不写注册表，也不要求管理员权限。

## 使用方法

> ⚠ **Team / Workspace（团队／工作区）账号首次添加：**
>
> 请从 Qiehao 的“添加账号”流程发起官方 OAuth（开放授权），并在官方登录页面确认选中了预期的 Team 工作区。
>
> 不要只凭邮箱、显示名称或 Plus / Team 套餐字样推断工作区身份。Team / Personal（个人）上下文无法可靠确认时，Qiehao 不会把该身份当作已验证账号保存；请按界面提示重新通过官方流程登录。

v1.1.1 首次添加与后续添加账号均优先使用官方浏览器流程：

1. 完全退出 Codex Desktop。
2. 打开 Qiehao，点击“添加账号”。
3. Qiehao 通过官方 Codex app-server 发起 ChatGPT OAuth；默认浏览器打开官方登录页。
4. 在浏览器完成目标账号登录；等待时可按 Esc 取消。
5. Qiehao 完成身份验证后，请输入本地名称；凭据安全保存后才完成添加。

官方登录和身份读取可能需要等待；v1.1.1 的登录等待预算最长约 180 秒（实际耗时取决于网络和官方响应），请勿连续点击“添加账号”或并行启动多个 Qiehao。若超时，按下方 OAuth 异常恢复说明处理，不要假定授权状态完全没有变化。

一般无需先启动 Codex Desktop 登录。添加第二个或后续账号重复上述流程，浏览器中请选择目标账号；新账号凭据不会回存到先前的 Active Profile（当前活动档案）。

如果当前 Codex 版本不支持 Managed Login（托管登录）、官方协议不兼容，或直接 OAuth 添加暂时不可用，请按界面提示使用旧兼容流程：先在 Codex Desktop 中通过官方流程登录或切换到目标账号，确认登录成功，完全退出 Codex 客户端，再返回 Qiehao 添加账号。不会静默把旧账号当作新账号；不承诺新 OAuth 路径永久可用。

Team / Workspace（团队／工作区）账号直接 OAuth 添加后，如工作区识别正常，可以正常保存使用。仍请保留上面的首次添加注意事项；当前真人验收不是对未来工作区选择永不变化的保证。

这里的“退出 Codex”是关闭 Codex 客户端，包括可能仍在运行的系统托盘进程，不是注销当前登录账号。每个账号只需要成功添加一次；以后在已保存账号之间切换时，直接在 Qiehao 选择目标档案并点击“切换账号”，不需要重复 OAuth 登录。切换前仍应按界面提示完全退出 Codex，切换完成后再由用户手动重新启动 Codex。

不要把关闭主窗口等同于完全退出；Codex 仍可能驻留在系统托盘。Qiehao 不会把任务管理器强杀当作正常流程。

## 账号身份与异常恢复（重要）

Qiehao 会分别核对**已保存的本地账号档案**、**Qiehao 记录的当前活动档案**和 **Codex 当前实际登录身份**。这三者不是同一件事；账号显示名称、邮箱或旧额度数字都不能单独证明身份一致。发现不一致时，程序应停止相关写入或额度查询，而不是猜测、覆盖或自动换号。

### 官方 OAuth 报告失败，但登录状态可能已经改变

官方 OAuth（开放授权）完成通知被拒绝、超时或读取失败，**不一定代表 Codex 当前授权完全没有变化**。如果当前版本在失败后显示“登录异常后核对身份”，请按以下顺序处理：

1. 正常退出 Codex Desktop，确认它已完全退出；不要只关闭主窗口或强制结束进程。
2. 只有在 Qiehao 明确提供时，选择“检查当前登录身份（只读）”。这一步用于核对当前实际身份，不会立即创建档案，也不会把当前凭据写入已有档案。
3. 如果身份已可靠验证且尚未保存，Qiehao 才会要求输入本地名称并再次明确确认“保存新档案”。这是新增独立档案，不覆盖已有档案；如果身份已经存在，则不会重复创建。
4. 如果身份无法验证、授权在检查后发生变化，或检查结果过期，Qiehao 不会保存新档案。按界面提示重新通过官方流程登录，不要手工编辑或复制 auth.json，也不要删除 profiles/、state/。

这条异常恢复路径不要求先把 Qiehao 的活动档案强行同步成当前身份；但它**不绕过身份验证**。浏览器显示登录成功，不等于 Qiehao 已经保存账号；请以 Qiehao 最终结果和账号列表为准。

### 当前 Codex 身份与活动档案不一致：Plus / Team 特殊恢复

如果 Qiehao 检测到当前 Codex 实际登录是已确认的 Personal Plus，而当前活动档案是身份完整、工作区已确认的 Team 档案，可能会出现“恢复已保存的 Team 登录”确认框。这是一个**范围严格受限的 Plus → 已保存 Team 恢复**，不是通用的身份修复按钮。

- 确认前先读清提示：确认后会用已保存的 Team 凭据替换当前 Codex 的 Plus 登录状态；已保存的 Team 档案本身不会被删除或改写。
- 如果当前 Plus 登录状态尚未另存为档案，恢复后可能需要再次通过官方 OAuth 登录 Plus。若你要保留当前 Plus 登录，先取消，不要确认替换。
- 如果当前身份、Team 工作区、目标档案完整性或退出状态不符合条件，程序会停止恢复，不应尝试绕过提示。
- 如果结果显示“本地 Team 已切换，但官方身份尚未验证”，这只说明本地凭据和活动记录已提交，**不等于官方登录验证成功**。先重新核对实际身份，不要连续重复切换。
- 如果明确提示“请勿启动 Codex／需要人工检查”，必须遵守：不要启动 Codex，不要再次添加、切换或恢复，也不要手工修改认证文件。

### 额度显示旧数据或提示身份不一致

额度是按账号身份绑定的快照，不是账号身份的证明，也不是实时监控：

- “当前登录与活动档案不一致，已暂停额度查询”：说明身份核对未通过，额度请求已暂停；先处理身份不一致，不要把显示的旧数字当作当前账号额度。
- “旧额度缓存归属未验证”或“历史缓存”：旧缓存缺少足够的身份绑定证据，可能保留用于查看历史，但不能据此判断当前账号的套餐或剩余额度。程序不会擅自把旧缓存重新归属给另一个账号。
- “接口已响应，但未取得可显示额度”：不代表剩余额度为 0；可能是官方接口没有返回可显示的额度窗口。

身份恢复并通过核验后，再对当前账号手动刷新额度。额度异常不代表账号档案被覆盖，也不应成为反复切号的理由。

## 常见问题

### 如果提示 Codex 正在运行怎么办？

如果 Codex 客户端刚刚关闭，Windows 可能仍需要少量时间释放后台进程。

此时 Qiehao 可能提示“Codex 正在运行”。

请稍作等待后再次尝试切换或删除操作。

为避免 Windows 进程状态刷新延迟影响判断，请避免在短时间内连续快速切换多个账号。

建议等待当前切换完成、客户端状态稳定后，再进行下一次切换。

### Windows Sandbox Service（沙箱服务）一直存在怎么办？

新版 Codex Windows 可能常驻 `codex-windows-sandbox-service.exe`。v1.1.1 严格验证官方持久沙箱服务；经确认可信的服务本身不会阻塞账号操作。通常不需要手动结束它、禁用服务或修改 Windows 服务设置。真正的 Codex Desktop／外部 Codex 执行进程仍会安全阻止账号操作；无法可靠分类时继续安全拒绝。

### 本地切换完成，但登录状态暂未验证是什么意思？

本地 Profile（档案）切换完成后，Qiehao 尝试通过官方 `account/read` 验证登录状态。验证成功才显示切换成功；网络或官方接口暂时超时时显示“本地账号已切换，登录状态暂未验证。”这不代表本地切换失败，可以正常启动 Codex 查看，或稍后点击“验证”。真正的身份不一致仍按安全回滚策略处理。

### Codex Desktop 重新打开后显示未登录怎么办？

这是当前仍需观察的已知限制：Codex Desktop 偶尔可能在重新打开后显示未登录；官方 OAuth 的完成通知也仍可能被拒绝。本次源码修复改善了失败后的身份只读核对和明确保存流程，但**没有承诺消除 Codex Desktop 的所有登录异常，也不能保证官方服务端一定接受某次登录状态**。

先看 Qiehao 的最终结果：本地档案已保存、切换已提交、官方身份已验证，是不同状态。先等待客户端初始化；若持续显示未登录，再正常完全退出并重新打开。不要连续重复添加／切换，不要删除旧档案或认证文件，也不要手工复制 auth.json。必要时完全退出后按界面提供的“验证”入口检查，并仅查看或提供已脱敏的日志、提示及错误代码；切勿附带真实凭据。若出现“请勿启动 Codex／需要人工检查”，优先遵守停止提示。

### Qiehao 在添加或切换过程中意外关闭怎么办？

程序窗口消失本身不能证明操作成功或失败。重新打开 Qiehao，先查看账号列表、当前活动档案和界面状态；在确认前不要连续重复添加或切换。如果此前出现“请勿启动 Codex／需要人工检查”，不要启动 Codex。保留本机 profiles/、state/、logs/ 和 backup/，不要清理或手工改写；这些目录可能包含恢复所需的本地数据，但不要上传到公开 Issue。

### 什么时候必须停止并等待人工检查？

只要 Qiehao 明确提示“请勿启动 Codex，需要人工检查”，就不要启动 Codex，也不要再次执行添加、切换、恢复或删除操作。不要手动替换 auth.json，不要删除或重命名 profiles/、state/ 中的文件。保留原状，通过私密、安全的方式提供已脱敏的提示文字和错误代码；真实 Token、邮箱、账号 ID、Cookie、认证文件及完整日志不得公开上传。

## 更新

普通用户推荐使用 GitHub Releases 提供的新版 Release ZIP 更新。以下适用于从 v1.0.3 或 v1.1.0 升级到 v1.1.1：

2. 下载 v1.1.1 Release ZIP，并核对 SHA256。
3. 将新版 ZIP 的内容完整解压覆盖到原 Qiehao 目录；如系统询问，只覆盖同名程序文件。
4. 保留原目录中的 `profiles/`、`state/`、`logs/` 和 `backup/`，不要为了升级删除整个旧目录。
5. v1.1.1 包含重新编译的 `Qiehao.exe`，覆盖后可直接双击；`Start-Qiehao.cmd` 仍是备用入口。正常覆盖程序文件不需要重新添加已保存账号。

如果选择解压到全新的目录，需要手动复制旧目录的 `profiles/` 和 `state/`，才能继续看到原有账号。仅限同一台 Windows 电脑、同一个 Windows 用户和本机 DPAPI CurrentUser 保护环境；`logs/` 和 `backup/` 不是恢复账号列表所必需。不要把这些私有目录上传到公开位置。

发布 ZIP 不包含 `profiles/`、`state/`、`logs/` 或 `backup/`；正常覆盖程序文件不会删除这些私人运行数据。不要跨电脑或跨 Windows 用户直接迁移 DPAPI 档案。

### v1.1.1 可靠性与回滚说明

v1.1.1 保持 Profile 格式与 DPAPI CurrentUser 兼容，包含已通过真人验收的账号流程修复和薄 EXE 启动器。

该版本系列修复账号操作结束后的界面同步：“当前账号”直接读取已经提交的本地 Active Profile，无需启动 Codex Desktop 来刷新；官方验证状态与当前账号标记分开显示，过期刷新结果不能覆盖较新的状态。连续添加失败／取消能够安全收尾；常驻 Windows Sandbox Service（沙箱服务）与真实 Desktop 进程分开判断。

切换的本地事务与官方登录状态验证分别报告。验证超时不会回滚已经完成的本地切换，也不会显示“切换成功”；会显示“本地账号已切换，登录状态暂未验证”。明确失效提示重新登录，身份不一致安全停止并回滚。稳定 `account/read` 只能证明当前官方进程加载的认证状态，不能保证未来服务端请求或 Desktop 工作区选择永不变化；未使用实验 workspaceRouting，也不使用邮箱作身份主键。

保留现有空间账号首次添加警告，Team 工作区的长期真人验证数据仍不够多。额度只作辅助，不阻塞添加、切换、删除和验证；失败可手动刷新，显示最后成功快照，不进行后台高频轮询。验证 Token 刷新后仅在严格身份一致时安全回存原始认证字节，Profile 格式与 DPAPI CurrentUser 不变。

如需回退软件版本，优先保留当前最新的 `profiles/` 和 `state/`，只回退程序文件。认证令牌可能已被 Codex 刷新，不应优先恢复陈旧认证备份。v1.1.1 的 Profile 格式与 v1.0.3 兼容；未来若改变格式，必须另行设计迁移和回滚。

不要直接在 ZIP 压缩包内运行，也不要为了更新而删除包含本机运行数据的旧目录。`profiles/`、`state/`、`logs/` 和 `backup/` 可能包含当前 Windows 用户在本机产生的私有运行数据；确认新版正常工作并妥善处理这些数据前，不要删除旧目录。

通过 Git 管理源码的高级用户应先检查：

~~~powershell
git status --short
~~~

确认没有本地源码修改后，再执行：

~~~powershell
git pull --ff-only
~~~

`--ff-only` 只允许 Fast-forward（快进）更新；如果本地历史已经分叉，Git 会安全停止，而不是自动产生 merge commit（合并提交）。如果 `git status --short` 显示源码文件有本地修改，应先自行审查并妥善处理，不要强制覆盖。

## Privacy（隐私）

- Local-first（本地优先）：档案、状态和额度缓存保存在本机运行目录中。
- Qiehao 账号配置使用 Windows DPAPI CurrentUser（数据保护 API，当前用户作用域）保护，并绑定当前 Windows 用户和本机保护环境。
- 不要直接把 `profiles/` 目录复制到另一台电脑使用；即使另一台电脑使用相同的 Windows 用户名，也不能假定这些文件能够解密。
- Browser/PWA untouched（浏览器/PWA 不受影响）。
- 本项目未加入 telemetry（遥测）或 analytics（分析统计）。
- 本项目不运营中转服务器。
- 不对非活动账号发起额度查询。
- `profiles/`、`state/`、`logs/`、`backup/`、`auth.json`、DPAPI 容器和额度缓存均不得提交到 Git。

用户应妥善保护自己的 Windows 账号、Codex 登录和本机环境。不要把 `profiles/`、`state/`、`logs/`、`backup/` 或 `auth.json` 上传到 GitHub、网盘、聊天工具或公开 Issue（议题），也不要粘贴 Token（令牌）、邮箱、账号 ID、Cookie 或含凭据的日志。
